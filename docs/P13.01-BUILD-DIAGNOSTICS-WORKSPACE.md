# P13.01 — Build Diagnostics Workspace

> **Current UX note:** Build History Diagnostics now opens in an accessible modal inside BuildKit. The underlying P13.01 diagnostic data/tabs remain unchanged.

> Milestone: **M13 — Advanced Diagnostics & Operations**  
> Status: **Implemented**  
> Product surface: **BuildKit → Build History → Diagnostics**

## Objective

Turn Build History from a passive list into a diagnostic workspace that answers:

- What was built?
- Which Buildx record is this?
- How long did it take?
- How many steps completed and how many were cached?
- What did BuildKit log for each step?
- Where did the build fail?
- Is the failure consistent with a known operational pattern?
- Can the same record be opened in Docker Desktop for deeper native inspection?

## Official Buildx commands used

```text
docker buildx history inspect --format json <REF>
docker buildx history logs --progress plain <REF>
docker buildx history open <REF>
```

Docker execution remains in Electron Main. The Renderer receives only typed diagnostic data through Preload IPC.

## Workspace tabs

### Overview

Displays:

- Status
- Duration
- Completed / total steps
- Cached / total steps
- Context
- Dockerfile
- Target
- Platforms
- VCS repository / revision
- Build ID / ref
- Started / completed timestamps
- Materials
- Attachments such as provenance / SBOM metadata when Buildx exposes them

### Logs

Displays full `--progress plain` output with local search.

### Steps

Parses Buildx plain-progress markers:

```text
#1 [internal] load build definition
#1 DONE 0.1s
#2 [internal] load metadata
#2 CACHED
#3 [build 1/3] RUN npm ci
#3 ERROR: ...
```

Each parsed step is classified as:

```text
RUNNING
DONE
CACHED
ERROR
```

### Cache

Displays:

- Cached steps
- Total steps
- Cache-hit percentage
- Executed-step count
- Individual `CACHED` markers found in Buildx logs

### Timing

Displays:

- Started
- Completed
- Human-readable duration
- Duration in milliseconds
- Cache-vs-executed step ratio

`Duration` returned by `history inspect --format json` is normalized from nanoseconds to milliseconds.

### Error Analysis

Rule-based and evidence-driven. Current signatures include:

- Failed BuildKit step / `failed to solve`
- No space left on device / ENOSPC
- Permission denied / EACCES
- DNS / network failures
- npm / package restore failures
- Missing file / build-context problems
- Non-zero process exit codes

Every finding contains:

```text
Severity
Title
Evidence from real logs
Recommended action
```

If no known signature is found, the advisor explicitly says that it cannot identify a known pattern rather than guessing.

## Security boundaries

- Renderer does not run Docker CLI.
- Build references are validated in Main IPC.
- `inspect`, `logs`, and `open` execute in Electron Main.
- Diagnostics are read-only except for `history open`, which only opens Docker Desktop.
- No automatic rebuild is attempted.

## Why automatic Re-run is intentionally excluded

A Build History record does not reliably preserve every original invocation input needed to reproduce a build safely, including arbitrary build args, secrets, SSH mounts, outputs, environment-dependent contexts, and caller-specific flags.

P13.01 therefore does **not** fabricate a build command or silently re-run a build from incomplete metadata. A future re-run feature should require an explicit reproducible build recipe or saved user-defined build command.
