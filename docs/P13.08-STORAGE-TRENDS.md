# P13.08 — Storage Trends

> Milestone: M13 — Advanced Diagnostics & Operations  
> Status: Implemented

## Objective

Add local historical storage visibility so DockScope can answer not only **how much storage Docker uses now**, but also:

- Is storage growing?
- Which category is growing?
- Did cleanup actually reduce Docker allocation?
- Did the physical Docker Desktop VHDX shrink after cleanup?
- How much reclaimable space exists relative to current allocation?
- What were the peak Docker/VHDX values over 24 hours, 7 days, or 30 days?

## Sampling Architecture

```text
Electron Main
      ↓
StorageTrendService
      ↓
docker system df --format json
      +
Windows VHDX metadata
      ↓
dockscope.sqlite3 / storage_trends
```

Sampling is owned by Electron Main so it does not depend on the Storage page being mounted.

## Schedule

```text
Startup sample attempt
        +
Every ~15 minutes while application is running
```

Scheduled samples are de-duplicated when the most recent sample is less than ten minutes old.

The user can explicitly choose **Record sample now** to establish a baseline or capture a post-cleanup/post-compaction state.

## Retention

History is bounded:

```text
Retention window: 31 days
Hard sample cap:  3,100 samples
```

The expected 15-minute sampling cadence is approximately:

```text
96 samples/day
≈ 2,976 samples/31 days
```

The hard cap protects against excessive growth if sampling behavior changes.

## Persistence

Samples are stored in the shared Knex/SQLite database under Electron `userData`:

```text
dockscope.sqlite3
└── storage_trends
```

Persistence uses Knex transactions against SQLite. The `captured_at` column is indexed for historical range retrieval.

No data is sent to an external telemetry service.

## Sample Schema

Each sample includes:

- Capture timestamp
- Images bytes
- Container writable-layer bytes
- Local Volume bytes
- Build Cache bytes
- Total selected Docker allocated bytes
- Total selected Docker reclaimable bytes
- Physical VHDX bytes
- Host drive free bytes
- Image count
- Container count
- Volume count
- Build Cache record count

## Docker Allocation

Docker allocation is calculated from the storage categories returned by Docker:

```text
Images
+
Containers
+
Local Volumes
+
Build Cache
=
Docker allocated
```

This is intentionally distinct from the physical VHDX file size.

## Why Docker Allocation and VHDX Differ

Docker Desktop on Windows can reclaim logical Docker objects without immediately reducing the VHDX file size.

Example:

```text
Before cleanup

Docker allocation: 70 GB
VHDX:              85 GB

After cleanup

Docker allocation: 42 GB
VHDX:              85 GB

After compaction

Docker allocation: 42 GB
VHDX:              51 GB
```

Storage Trends makes this difference visible instead of assuming Docker cleanup and host-disk recovery are the same operation.

## Ranges

The UI supports:

### 24 hours

Best for:
- sudden growth;
- a single development/build session;
- before/after cleanup comparison.

### 7 days

Best for:
- repeated local builds;
- image churn;
- Build Cache growth;
- database/volume growth during development.

### 30 days

Best for:
- longer Docker Desktop growth patterns;
- VHDX drift;
- persistent storage trend review.

## Charts

### Docker Allocation vs VHDX

Two lines:

- Docker allocated bytes
- Physical VHDX bytes

### Docker Storage Composition

Four lines:

- Images
- Volumes
- Build Cache
- Containers

## Renderer Performance

The service returns all samples in the selected range for accurate summary calculations.

The SVG chart downsamples to at most approximately 240 rendered points.

This avoids creating thousands of SVG circles/path points while preserving the overall trend shape.

Summary values continue to use the complete selected-range data.

## Summary Metrics

The Storage page shows:

- latest Docker allocated;
- current Docker reclaimable;
- latest VHDX size;
- host-drive free space;
- sample count;
- Docker allocation delta;
- VHDX delta;
- peak Docker allocation;
- peak VHDX.

## Latest Composition

The most recent sample shows:

- Images bytes/count
- Containers bytes/count
- Volumes bytes/count
- Build Cache bytes/count

## Sampling Failure

A failed Docker storage query does **not** add a zero/invalid trend point.

This prevents a temporary Docker Engine outage from appearing as a false storage collapse in historical charts.

## Diagnostics Bundle

P13.07 Diagnostics Bundle Export now includes:

```text
storage/storage-trends-30d.json
```

with the current 30-day Storage Trend data.

## Privacy

Storage Trends stores aggregate storage measurements and counts.

It does not collect:

- volume contents;
- filenames inside volumes;
- container filesystem contents;
- application records;
- network traffic;
- external telemetry identifiers.

## Safety

Sampling is read-only.

It does not automatically:

- prune images;
- remove containers;
- remove volumes;
- remove Build Cache;
- compact the VHDX.

VHDX compaction remains a separate typed-confirmation operation executed through Task Center.
