# P13.06 — Operation Task Center

> Milestone: M13 — Advanced Diagnostics & Operations  
> Status: Implemented

## Objective

Centralize long-running Docker and storage operations so they survive page navigation, expose live output/progress, support cancellation where safe, and retain bounded local history.

## Architecture

```text
Renderer
  ↓ allowlisted task request
Preload
  ↓ typed IPC
Electron Main
  ↓ TaskCenterService
Child Process / Windows Storage Workflow
```

Renderer cannot submit an arbitrary command string.

The Main process maps validated operation kinds to known commands.

## Supported Operations

- Image Pull
- Compose Pull
- Compose Build
- Compose Up
- BuildKit Prune
- Safe / Balanced Cleanup
- VHDX Compact

## Task States

```text
Queued
Running
Completed
Failed
Cancelled
```

Each task records:

- Task ID
- Kind
- Title
- Resource context
- Source page
- Command summary
- Created / Started / Completed timestamps
- Duration
- Progress percentage when available
- Latest progress text
- Bounded process output
- Exit code
- Cancellable flag
- Cancellation request state

## Live Updates

TaskCenterService emits task-change events.

Main broadcasts:

```text
tasks:changed
```

to application windows.

Renderer subscribes through Preload and updates the task table without polling.

## Persistence

Task history is stored in the shared Knex/SQLite database under Electron `userData`:

```text
dockscope.sqlite3
└── operation_tasks
```

Task updates use SQLite UPSERTs; streamed task output updates only the affected task row.

Retention is bounded to the latest 500 tasks.

If the application restarts while a task was persisted as Queued/Running, that record is changed to Failed/Interrupted. The old child process is not reattached.

## Output Safety

Process output is:

- bounded to 200,000 characters per task;
- redacted before persistence for common password, token, API key, bearer token and connection-string patterns.

This reduces accidental secret retention while still preserving diagnostics.

## Cancellation

Docker CLI tasks are cancellable.

Cancel:

```text
Task Center
  ↓
IPC
  ↓
TaskCenterService
  ↓
child.kill()
```

VHDX compaction is intentionally not cancellable after start because interrupting Docker/WSL/virtual-disk operations can produce an ambiguous system state.

## Cleanup

Safe/Balanced Cleanup is implemented as a sequenced task:

```text
container prune
image prune
network prune
builder prune
[optional image prune --all]
```

Volumes are never included.

Progress is updated by cleanup step.

## Existing Resource Integration

Long-running actions now enqueue into Task Center from:

### Compose Workspace

- Pull
- Build
- Up
- Up + Build

### BuildKit

- Safe prune
- Prune all

### Cleanup Advisor

- Safe cleanup
- Balanced cleanup

### VHDX Manager

- Compact VHDX

The Task Center launcher can also start Image Pull and the other supported operations directly.

## Security

Task request validation in Main includes:

- fixed allowlist of operation kinds;
- validated image reference;
- validated Compose project shape;
- bounded BuildKit keep-storage value;
- `.vhdx` path requirement;
- no arbitrary shell command field.

`spawn(..., shell: false)` is used.

## UI

Task Center includes:

- summary cards;
- operation launcher;
- task search;
- status filter;
- operation-kind filter;
- 10-item pagination;
- live progress;
- running duration;
- task output detail;
- cancel;
- clear completed/failed/cancelled history;
- deep-link back to originating resource where available;
- contextual in-page Guide.

## Progress Semantics

Some Docker operations expose numeric percentage output; that is shown as a determinate progress bar.

Commands without reliable percentage information use:

- latest progress line;
- indeterminate progress animation.

Build-like output recognizes BuildKit step markers.
